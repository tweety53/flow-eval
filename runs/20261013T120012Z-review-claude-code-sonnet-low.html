### Summary
This diff adds three behaviours:
- **Preferences PUT:** `updatePreferences` now carries an optional `sessionView`.
- **`load()`:** it now adopts two fields, each guarded by its own stale-write counter.
- **`chooseSessionView`:** a new optimistic write. It is serialised on `sendMutex` and reads `unitWrite.confirmed` inside the lock, so it sends the unit that was last confirmed.

I walked each through all four lenses.

- **Error return:**
  - A failed `getPreferences` is handled as before: `loadFailed` is set and the user is notified.
  - A failed PUT is routed through `viewWrite.onFailure` and reverts to the confirmed mode, or sets `loadFailed` if nothing is confirmed.
  - With no confirmed unit, `error(...)` raises a failure before any PUT is sent, so a stored LBS is never overwritten with the default KG. The failure message is user-facing.
  - Cancellation is excluded by `onFailureNotCancelled`.
- **Timeout:** the PUT runs while holding `sendMutex`, so a hung request blocks every later unit and mode write. This is the existing pattern from `chooseUnit`, and the diff adds no new unbounded call. I did not check the Ktor client's timeout configuration.
- **Partial write:**
  - Each PUT is a single request, with no multi-step state on the server side.
  - Locally, the unit and mode fields move through separate `OptimisticWrite`s. `load` adopts each field only if no write to that field succeeded since the load began, so a stale load cannot clobber a newer write.
  - A load started before a unit write can still adopt its view. That is correct, because a unit write never changes the view.
- **Concurrent re-entry:**
  - Rapid taps are serialised by the mutex, and the PUT is idempotent.
  - The `unitWrite.confirmed` read happens inside the lock. This avoids sending a unit that is still queued, and the added test covers that case.

### Issues

#### Critical (Must Fix)
None.

#### Important (Should Fix)
None.

#### Minor (Nice to Have)
- **`SettingsState.kt`, `chooseSessionView`, error return.** The write adopts `it.sessionView` from the answer, and the answer defaults to `FOCUS` when the key is missing (`WorkoutModels.kt`: `sessionView = SessionView.FOCUS`). If the server is an older build that ignores or omits `sessionView`, a PUT of `QUICK` succeeds and returns no key. The client then adopts `FOCUS`, so the user's tap silently snaps back with no notification.
  - Fix sketch: make the response field nullable and treat a missing value as a failed write.
  - Reproducer: none — it needs a server build that omits `sessionView`. You can approximate it by making `FakeWorkoutApi.updatePreferencesResult` return `WorkoutPreferences(KG)` after `chooseSessionView(QUICK)` and asserting that a notification is raised. The current code raises none.

### Assessment
**Ready for the human gate?** Yes
**Reasoning:** The new write path handles failure, stale loads and queued writes correctly, and the added tests cover the failed-load and queued-unit races. The only gap is the minor version-skew case above, and the lock-held PUT has no new timeout exposure.

### Summary
This diff adds a `sessionView` preference. It covers the API, the model, `SettingsState.chooseSessionView` with `load` changes, and the Settings row. I checked it against `OptimisticWrite` and `SettingsState.kt`, but did not open `requests.apiCall` or the client's timeout configuration.

- **Error return:** `chooseSessionView` handles errors. The `error(...)` raised when no unit is confirmed is caught by `runCatching` and routed to the failure outcome. `load` keeps its stale-response guards for both fields.
- **Partial write:** the PUT is a single request, so there is no torn state. The one exception is the ambiguous-failure case below.
- **Concurrent re-entry:** `sendMutex` serialises the two write types. Reading `unitWrite.confirmed` inside the lock is correct against writes from this client.
- **Timeout:** no new boundary call is added. It reuses `updatePreferences`, and I did not inspect the client's timeout configuration.

The remaining gaps come from the backend requiring `displayUnit` on every PUT. That makes a mode-only change write the unit as well.

### Issues

#### Critical (Must Fix)
None.

#### Important (Should Fix)

1. **`SettingsState.kt`, `chooseSessionView`:** concurrent re-entry, with an ambiguous-failure variant.
   - **Scenario 1, two devices:** device A loads with KG confirmed. Device B changes the unit to LBS. The user then taps Quick on A. A's PUT sends `displayUnit=KG`, which silently reverts B's LBS. The new "mode-only" action therefore mutates the unit using a stale cached value. The returned unit is also deliberately not adopted, so A keeps showing KG, but the server now holds KG.
   - **Scenario 2, ambiguous unit write:** a `chooseUnit(LBS)` PUT times out or drops after the server applied it. The client treats it as failed and reverts `confirmed` to KG. A following mode write then sends KG and overwrites the stored LBS.
   - **Fix sketch:** have the server accept a PUT with only `sessionView` (make `displayUnit` optional). Failing that, re-fetch `getPreferences()` inside `sendMutex` just before the mode write and use that unit.
   - **Reproducer:** none — needs the real backend. In the fake, you can show Scenario 2 by queuing `updatePreferencesResult = failure` for `chooseUnit(LBS)` and then calling `chooseSessionView`. `api.updatePreferencesRequests` will end with `[LBS, KG]`, so the mode write sent the stale KG.

#### Minor (Nice to Have)

2. **`SettingsState.kt`, `chooseSessionView`:** error return. When the load has failed (`confirmed == null`), the write is refused with `NOTHING_CONFIRMED`. `viewWrite.value` stays at the optimistic Quick, so the control shows a mode that was never saved. The `hasLoaded` gate probably hides this today. If a failed load can still render the row, the control will show a lie.
   - **Fix sketch:** revert the value to Focus, or leave the control disabled while `loadFailed` is set.
   - **Reproducer:** none — the `hasLoaded` gate would have to be bypassed. The test `a workout mode write after a failed load…` does not assert `state.sessionView`.

### Assessment
**Ready for the human gate?** With fixes
**Reasoning:** The write ordering and stale-load handling hold up. The one real gap is that the mode write sends the unit it last saw, so it can overwrite a unit changed by another device or by an unconfirmed write. That needs either a server-side partial update or a fresh read before the PUT.

### Summary
This diff adds a `sessionView` field to the preferences API and a `chooseSessionView` write path in `SettingsState`. It also changes how `load` handles stale results, and adds a Settings row. I read the diff only and did not open `OptimisticWrite`, `Sequencer` or `onFailureNotCancelled`. I judged them by their names and call sites, so the cancellation and token handling below rests on that.

The four lenses apply as follows:
- **Error return.**
  - Both a failed `load` and a failed `PUT` are surfaced and revert correctly.
  - `error(...)` inside `runCatching` is caught and turned into a notification.
  - With no confirmed unit, no request is sent.
- **Timeout.** `sendMutex.withLock` has no bound of its own, so a mode write waits behind any hung unit write. The unit path already behaved this way, and the diff adds no new external call. Nothing new to report.
- **Partial write.** There is one PUT per action. The "carry the confirmed unit" design avoids a torn write that would clobber the stored unit with a default. Failed writes revert to the last confirmed value.
- **Concurrent re-entry.** Writes within one process are serialised by `sendMutex`, and the test covers the queued-unit case. The gap is across devices (see Important).

### Issues

#### Critical (Must Fix)
None.

#### Important (Should Fix)
- **`SettingsState.kt`, `chooseSessionView` (`unitWrite.confirmed` sent in the PUT)** — *concurrent re-entry (cross-process).*
  - **Scenario:** Device A loads with unit KG. On device B the user changes the unit to LBS. Back on device A, the user taps Quick. Device A sends `displayUnit=KG, sessionView=QUICK`, which silently reverts the unit to KG on the server. Device A then drops the returned unit, so nothing on that device shows the change.
  - **Why it's new:** Before this diff, a PUT only ever carried a value the user had just chosen. Now a PUT can carry a stale value the user never touched.
  - **Fix sketch:** Have the backend accept `displayUnit` as optional, with null meaning unchanged, which matches how `sessionView` already works. Otherwise, call `getPreferences()` inside the mutex just before the PUT and use that unit.
  - **Reproducer:** none — needs two clients against a real server. A fake-API test could simulate it by changing `preferencesResult` after `load()` and then calling `chooseSessionView`; the PUT would still carry the old unit.

#### Minor (Nice to Have)
- **`SettingsState.kt`, `load` success branch** — *error return / state.**
  - **Scenario:** If a unit write succeeded during a load but no view write did, `loadFailed` is not cleared (`noWriteSucceeded` is false), even though the view value was adopted. A previously failed load can then stay flagged as failed while the view has been refreshed.
  - **Fix sketch:** Clear `loadFailed` when either field was adopted.
  - **Reproducer:** none — benign and unlikely, since the successful write path already clears `loadFailed` itself.
- **`SettingsState.kt`, `chooseSessionView`'s `onSuccess`** — *error return.*
  - **Scenario:** If `viewWrite.onSuccess` reports the answer as stale, nothing is logged. This is the same as the unit path and is not an issue on its own.
  - **Fix sketch:** None needed.
  - **Reproducer:** none — nothing to demonstrate.

### Assessment
**Ready for the human gate?** With fixes
**Reasoning:** The in-process failure handling is sound, and the new tests cover refusal, a failed load, and queue ordering. The one real gap is the cross-device lost update. A mode write now writes back a possibly stale unit that the user never chose. That is recoverable and not data loss, so it needs a decision from the human reviewer: make the backend field optional, or re-read the unit before the PUT.
