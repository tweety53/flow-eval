### Summary

The diff adds a `sessionView` field to the preferences GET/PUT, a Workout mode row in Settings, and `SettingsState.chooseSessionView`, which reuses the unit's `OptimisticWrite` and `sendMutex` pattern. I walked the four lenses over these behaviours:

- **Error return:** `chooseSessionView` wraps the send in `runCatching`, so the `error(...)` for an unconfirmed unit lands in the failure branch. `load()` keeps its stale-response guard and now also checks the view write. Both are handled.
- **Timeout:** the PUT runs under `sendMutex.withLock`. `GymieApiClient.kt:255` installs `HttpTimeout`, so the lock is bounded by the request timeout. A slow mode PUT can delay queued unit saves for that long, but it cannot hang indefinitely.
- **Partial write:** each save is a single PUT, and the client writes no local state of its own. The server's atomicity is outside this diff.
- **Concurrent re-entry:** the mode write reads `unitWrite.confirmed` inside `sendMutex`, so it never carries a unit that is still queued. Two mode writes are serialised, so the last one sent wins on the server.

The one real dependency this diff does not verify is that a unit-only PUT (no `sessionView` key) leaves the stored mode untouched. If the server treats a missing key as FOCUS, changing units would silently reset the athlete's mode.

The request timeout in `GymieApiClient` (HttpTimeout, lines ~255-258) bounds the `sendMutex` hold, so a hung PUT cannot block the queue forever. Error return on the unit lookup (`unitWrite.confirmed ?: error(...)`) is handled correctly: nothing is sent, and the failure is surfaced with `loadFailed` set.

1. **`shared/src/commonMain/kotlin/com/gymie/shared/ui/SettingsState.kt`, `chooseSessionView` (the `runCatching { sendMutex.withLock … }` / `.onFailureNotCancelled` chain)**

The screen leaves composition, or the scope is cancelled, while the PUT is in flight or queued behind `sendMutex`. `runCatching` captures the `CancellationException` as a failure. `onFailureNotCancelled` deliberately skips cancellations, so `viewWrite.onFailure(token)` never runs. `finally { viewWrite.end() }` only decrements the in-flight count. The client decodes FOCUS. `viewWrite.onSuccess(token, FOCUS)` then sets `confirmed = FOCUS` and `value = FOCUS`, so the athlete's Quick choice is silently reverted with no error. The same default also flows into `load()` via `adoptLoad`.

### Issues

#### Critical (Must Fix)
None.

#### Important (Should Fix)

**1. `SettingsState.kt` `chooseSessionView` (around lines 327–332): stale unit overwrites the server's stored unit after a lost response.**
- Lens: timeout / error return, combined with the non-atomic relationship between the two writes.
- Scenario: `chooseUnit(LBS)` sends a PUT. The server commits `LBS`, but the response is lost and the client times out. `unitWrite` reverts to `confirmed = KG` and the user sees a failure. The user then taps Quick. `chooseSessionView` reads `unitWrite.confirmed` (`KG`) and sends `PUT {displayUnit: KG, sessionView: QUICK}`. The server now holds `KG`, silently reversing the unit the user had just chosen. The user is told nothing about this second change, and the unit they can see on screen is the one they saw before the mode tap. Stored preferences are changed without the user's intent.
- Fix sketch: either (a) have the mode write refuse to send a unit when the last unit write failed without a confirmed server answer (mark the unit as "unknown" after a timeout rather than reverting to the old confirmed value), or (b) re-`load()` before sending the mode write when `unitWrite` has an unresolved failure. Option (a) is the smaller change: track "server state uncertain" on `onFailure` for timeouts (`SocketTimeoutException` / `HttpRequestTimeoutException`) and make `chooseSessionView` fail through the `error(...)` path in that case.
- Reproducer: none — this needs a new unit test in `SettingsStateTest.kt` where the fake's `updatePreferences` records a server-side write and then throws a timeout, followed by `chooseSessionView` and an assertion on the fake's stored unit. The test does not exist in the diff, so there is no current command that demonstrates it.

#### Minor (Nice to Have)

**2. `SettingsState.kt` `sendMutex` (around lines 247 and 327): one hung PUT blocks every queued write.**
- Lens: timeout.
- Scenario: a PUT takes the full `REQUEST_TIMEOUT_MILLIS` before failing. Every `chooseUnit` and `chooseSessionView` queued behind it waits that long, and the unit control shows a spinner through `isSaving`. The wait is bounded, so this is not a hang, but it is a latency cliff from the serialization.
- Fix sketch: none required; document the bound or surface a per-write indicator. Accept as-is if the timeout is short.
- Reproducer: none — it depends on the real HTTP timeout value, which the fake does not model.

**3. `SettingsState.kt` `load()` failure message (around line 276): a user-facing string constant was replaced with a literal.**
- Lens: error return (reporting).
- The message changed from `FailureMessages.COULD_NOT_LOAD_WEIGHT_UNIT` to `"Could not load your settings."`. This is a copy change that also affects the unit control's failure text. It is not a failure-path defect, but it is a silent UX change in a failure path.
- Reproducer: none — it is a string literal change, visible only in the UI.

- Lens: concurrent re-entry / interruption. `onFailureNotCancelled` skips cancellation, and `finally { viewWrite.end() }` is the only cleanup.
