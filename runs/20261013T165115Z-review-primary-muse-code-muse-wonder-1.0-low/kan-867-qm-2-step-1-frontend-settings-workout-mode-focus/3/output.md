#### Critical (Must Fix)

#### Important (Should Fix)

1. **File:** [SettingsState.kt](/work/shared/src/commonMain/kotlin/com/gymie/shared/ui/SettingsState.kt:295) — `chooseUnit`'s untouched success path still does `if (unitWrite.onSuccess(...)) loadFailed = false`, clearing the now-shared `loadFailed` for the unit field alone. Since this diff makes `loadFailed` also stand for the workout mode, the following sequence leaves the screen in a false "all is well" state: the initial `load()` fails (neither field confirmed, `loadFailed = true`, mode showing the unconfirmed `FOCUS` default behind the skeleton gate), the user taps a weight unit, that write succeeds and clears `loadFailed` — but the session view has still never been confirmed, so Settings now presents the default `Focus` as the stored mode with no retry affordance, when the server may hold `QUICK`. This is exactly the writer the shared-state step targets: it was correct when `loadFailed` meant "the unit is unknown" and is wrong now that it means "the settings are unknown." The symmetric new line 339 does not have the same exposure in practice (a mode write can only succeed once a unit is confirmed), but the fix should be symmetric anyway: only clear `loadFailed` when the other field is also confirmed (e.g. `unitWrite.confirmed != null && viewWrite.confirmed != null`), or track the retry flag per field. **Reproducer:** none — no existing test combines a failed load with a subsequent successful unit write while asserting `sessionView`/`loadFailed`; a new `SettingsStateTest` case (failed `load()`, then `chooseUnit(LBS)` against a fake whose stored view is `QUICK`, asserting `loadFailed` stays true or the view is re-read) demonstrates it, and the diff's own new tests do not cover this interleaving.

2. **File:** [WorkoutModels.kt](/work/shared/src/commonMain/kotlin/com/gymie/shared/domain/WorkoutModels.kt:691) — the new `SessionView` enum admits only `FOCUS` and `QUICK`, but the preferences endpoint already serves a third value: this repository's own fixtures answer `{"displayUnit":"KG","sessionView":"LIST"}` for `/api/workouts/preferences` ([GroupSessionLandingUiTest.kt](/work/shared/src/desktopTest/kotlin/com/gymie/shared/ui/groupsession/GroupSessionLandingUiTest.kt:114), [GroupSessionFloorUiTest.kt](/work/shared/src/desktopTest/kotlin/com/gymie/shared/ui/groupsession/GroupSessionFloorUiTest.kt:326)), and the archived KAN-71 artifacts define the stored server enum as `FOCUS, LIST`. Before this diff that key was ignored (`ignoreUnknownKeys = true` in [GymieApiClient.kt](/work/shared/src/commonMain/kotlin/com/gymie/shared/api/GymieApiClient.kt:245)); now any stored `LIST` preference makes decoding `WorkoutPreferences` throw, which fails `SettingsState.load()` outright and also breaks the workout editor's unit prediction at [WorkoutEditorScreen.kt](/work/shared/src/commonMain/kotlin/com/gymie/shared/ui/workout/WorkoutEditorScreen.kt:386), a consumer that does not care about the mode at all. The diff carries no backward-compatibility story for this: no `@SerialName`/alternate-name mapping of `LIST`, no tolerant unknown-value handling, and no serialization test feeding a legacy payload through `getPreferences`. If the backend change (KAN-865) migrates stored `LIST` rows and renames the value in lockstep, that needs to be stated and pinned by a decode test; otherwise map `LIST` onto the mode it now corresponds to. **Reproducer:** none — no existing test routes a `LIST` preferences payload through `WorkoutPreferences` decoding (the fixtures above hit endpoints whose screens no longer read preferences); a one-line decode test, `Json.decodeFromString<WorkoutPreferences>("""{"displayUnit":"KG","sessionView":"LIST"}""")`, throws `SerializationException` against this diff.

### Recommendations

- Add `SettingsStateTest` coverage for the two cross-field interleavings this change creates but does not test: a mode write racing a *failing* unit write (not only the succeeding one the diff tests), and a successful write of one field after a failed load leaving the other field unconfirmed (Important issue 1).
- Add a `WorkoutModelsSerializationTest` case pinning both wire directions for the new field on the response type — a payload without `sessionView` decoding to `FOCUS` is asserted only implicitly today — and, once issue 2 is decided, a legacy-`LIST` decode case.
- The per-field gating split inside `load()` (lines 270–272) is well judged; consider expressing the same per-field ownership for `loadFailed` rather than special-casing the clear sites, since this is the second field to share that flag and a third preference would repeat the bug.

**Ready for the human gate?** With fixes

**Reasoning:** The core design — per-field `OptimisticWrite` tracking, serialized sends, carrying the confirmed unit on mode writes, and refusing to guess a unit after a failed load — is sound and well tested on its happy paths, but the untouched `chooseUnit` success path now clears a shared retry flag for only one of the two fields it covers, and the new enum can fail to decode a preferences value the server already serves, with no migration or tolerance story in the diff.
