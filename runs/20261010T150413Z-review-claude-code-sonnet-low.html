The diff adds `sessionView` to the preferences PUT and a new `SettingsState.chooseSessionView`. That method sends the last confirmed unit under `sendMutex`. It also changes how `load()` reconciles two independent optimistic writes against a single GET.

I reviewed this from the diff alone and did not open `OptimisticWrite` or the HTTP client config. The lenses that applied:
- **Error return:** the no-confirmed-unit refusal and the failure outcome mapping. Both are handled and surfaced correctly.
- **Concurrent re-entry:** the mode write, unit writes and load are serialised by the mutex and sequence counters. The ordering test covers the queued-unit case.
- **Timeout:** the PUT runs while holding the mutex.
- **Partial write:** there is no multi-step write. The two fields go in one PUT, so there is no torn state.

### Issues

#### Critical (Must Fix)
None.

#### Important (Should Fix)
- **`SettingsState.kt`, `chooseSessionView` (the `unitWrite.confirmed` read and the `updatePreferences(displayUnit = unit, ...)` call). Lens: concurrent re-entry.**
  - **Failure scenario:** the backend requires `displayUnit` on every PUT, so a mode-only change must also write the unit. The unit it sends is the client's last confirmed value, which can be stale. The user changes the unit to LBS on another device, or an earlier unit PUT timed out after the server applied it. Then they tap Quick here. The PUT carries the old KG and silently reverts the server's unit. The response's unit is deliberately not adopted, so the UI never shows the revert. The result is wrong but recoverable, and it only appears on the next `load()`.

If that PUT hangs, every later unit or mode write queues behind it, and the Settings controls stay "saving" until the client's own timeout fires. `chooseUnit` already had this shape, but the new method adds a second caller.
  - **Fix sketch:** confirm that the Ktor client sets `HttpTimeout`. If it doesn't, wrap the send in `withTimeout`.
  - **Reproducer:** none — the diff doesn't show the client's timeout configuration.
